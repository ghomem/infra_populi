# Documentation list — single source
Behaviour that operators of the migrated code must know. Phase 3 runs observed it; none of it is a defect to fix.
Add an item only with its HQ source and the evidence (the Phase 3 result that showed it). Advisor-only file.

| # | class | what to document | evidence | source |
|---|---|---|---|---|
| 1 | backup_rsnapshot | Restores use the path `daily.0/etc/etc/…` (generally `<snapshot_root>/daily.N/<prefix>/<basedir>/…`). The template's `backup <basedir> ./<prefix>` combined with rsnapshot's `--relative` nests the source path under the prefix: a backup of `/etc` with prefix `etc` lands in `daily.0/etc/etc/hostname`. | `checks/results/backup_rsnapshot/20261116T113256Z-author.json` (daily-backup-executes effect: `/opt/puppet-infrastructure/backup/daily.0/etc/etc/hostname`) | HQ 2026-11-16 item 4 |
| 2 | nginx_proxy_smtp_auth_ppa (retired) | The class is gone from the module. It added the solidangle nginx PPA (Ubuntu 20.04 only) and its version-check script; on any newer release it broke `apt-get update`. A node that still declares it fails to compile; one that had it applied keeps the PPA's sources.list entry, which must be removed by hand. | batch-7 report item 2 (Launchpad `dists/<release>/Release` 200 for focal, 404 for jammy, kinetic and noble; run-1 `apt-get update` returned 100 on 24.04) | HQ 2026-11-17 ruling 3 |
| 3 | openvpn_server / network_vpn | On OpenVPN 2.6 (Ubuntu 24.04) the server receives LZO-compressed packets but sends uncompressed ones: `comp-lzo` gives receive-only compression unless `allow-compression yes` is set, which 2.6 discourages (compression attacks on the data channel). Clients keep connecting; only server-to-client traffic is uncompressed. Clients should drop compression at the cutover (see the cutover table). | `checks/results/openvpn_server/20261119T160852Z-author.json` (the-data-channel-is-compressed-both-ways: `server sends: uncompressed (1237 bytes per packet)`, `server receives: compressed (139 bytes per packet)`); reproduced in 20261119T161347Z-reviewer | HQ batch-14 ruling 2 |

| # | class | before cutover | why | source |
|---|---|---|---|---|
| 1 | openvpn_server / network_vpn (the VPN gateways) | On one gateway, read the `service_provider` fact and the running OpenVPN unit (`systemctl list-units 'openvpn*'`). | On a systemd host the baseline cannot compile against puppet-openvpn 8.3.0 (production's version): the duplicate unit and the missing `Service['openvpn']`. So the gateways run other content or are not systemd; the migrated class manages `openvpn-server@puppet_infrastructure`. | escalations/openvpn_server.md "HQ ruling 5" item 4 | HQ 2026-11-17 ruling 3 |
| 2 | nginx_base (with puppet-nginx 8.4.0) | The modules-enabled include now comes from the module (`include_modules_enabled => true`, ruled), as `include /etc/nginx/modules-enabled/*.conf;`. nginx_base's own `*` prepend is gone. A file in modules-enabled without the `.conf` suffix is no longer loaded (Debian packaging ships only `*.conf`). Check on one frontend: `ls /etc/nginx/modules-enabled`. | phase3 nginx_base run 1 (baseline content: 2 includes, nginx refused a dynamic module) and run 2 (ruled change: 1 include, nginx -t ok); rhel9 review: 1 include on RedHat | HQ batch-8 ruling 1 |
| 3 | nginx_base + nginx_frontend_mail (mail/stream frontends on Ubuntu 24.04) | On 24.04 the `nginx` package carries no dynamic modules. A mail/stream frontend needs `my_configs => {package_name => 'nginx-core', mail => true, stream => true}` (nginx-core depends on libnginx-mod-mail/-stream) or the libnginx-mod packages. With `stream => true`, puppet-nginx 8.4.0 also renders a stream access_log without a format, which nginx refuses: it waits on HQ's ruling (escalations/nginx_base.md, second section). | nginx_frontend_mail harness runs 2026-11-17 (module already loaded) and 2026-11-18 (log format is not specified) | batch-8 report; HQ batch-8 ruling 1 |
| 4 | nginx_base + nginx_frontend_mail (mail frontends) | Resolved by HQ ruling A1: `stream_access_log => 'off'` (no stream access log, as on 0.15). Separately, puppet-nginx 8.4.0 renders `proxy_smtp_auth` only when it knows nginx ≥ 1.19.4. It takes the version from the `nginx_version` fact, and from 1.16.0 when nginx is not installed yet. So a **freshly built** mail frontend's first agent run renders the SMTPS host without `proxy_smtp_auth on;` (backend logins are not passed on), and the second run completes it. Existing frontends have the fact and are unaffected. To build a frontend in one run, set `nginx_version` in nginx_base's `my_configs` (the lab fixture sets 1.24.0, Ubuntu 24.04's version). | Codex runs 2026-11-18 (fresh-node run 2 rendered the directive); mailhost_common.epp:27-29 and init.pp:447 of puppet-nginx 8.4.0; phase3 nginx_frontend_mail run 2 (SMTPS login reaches the backend) | HQ 2026-11-18 ruling A1 |
| 5 | hashman_web | A site supplies its own logo images: set `hashman::companylogo` and `hashman::companylogomail` in Hiera to files on the master (the class copies them into the portal). The repository carries no company logos; the lab uses placeholder files as a test asset (rules/test_asset_fixtures.txt). | the lab Hiera's example paths /path/to/logo.png and /path/to/logo-email.png; phase3 hashman_web logos-copied-from-hiera-sources | HQ batch-10 ruling 9 |
